# Установка Inst DM без опыта разработки

Эта инструкция рассчитана на человека, который раньше не разворачивал приложения. Вы сами владеете доменом, VPS, Meta-приложением и всеми данными. Установка использует только официальный Instagram API и не просит пароль от Instagram.

Проще всего пройти установку вместе с AI-агентом: отправьте ему текст из раздела «Установка через AI-агента» в [README](../README.md), и он проведёт вас по этим же шагам.

## Что понадобится

- Instagram Professional Account: **Creator** или **Business**;
- отдельный VPS за пределами РФ с Ubuntu 24.04 LTS или Ubuntu 26.04 LTS;
- минимум 1 vCPU, 2 ГБ RAM и 30 ГБ диска (на небольшом VPS установщик сам добавит файл подкачки);
- собственный домен или поддомен;
- доступ `root` к консоли сервера;
- 20–40 минут на Meta for Developers.

Facebook Page для сценария **Instagram API with Instagram Login** не требуется. Meta может менять названия и расположение разделов; ориентируйтесь на смысл пунктов и подсказки внутри панели.

## 1. Купите и подготовьте VPS

При создании VPS выберите:

- операционная система: `Ubuntu 24.04 LTS` или `Ubuntu 26.04 LTS`;
- зарубежный регион, где Instagram и Meta API доступны;
- один публичный IPv4-адрес.

В сетевом экране провайдера откройте входящие TCP-порты:

- `22` — SSH;
- `80` — получение HTTPS-сертификата;
- `443` — сайт и webhooks Meta.

UDP `443` можно открыть для более быстрого HTTP/3, но приложение работает и без него.

Скопируйте публичный IPv4. Не публикуйте пароль `root` и не отправляйте его разработчику приложения.

Проверьте, что у VPS нет уже работающего сайта на портах `80` и `443`: эти порты понадобятся `inst_dm` для HTTPS. Порт PostgreSQL `5432` открывать не нужно.

## 2. Настройте собственный домен

Купите домен у любого регистратора или используйте уже существующий. Проще выделить отдельный поддомен, например `dm.example.com`.

В DNS-панели создайте запись:

```text
Тип: A
Имя: dm
Значение: ПУБЛИЧНЫЙ_IP_VPS
TTL: Auto или 300
```

Если ставите приложение на корневой домен, вместо `dm` обычно указывают `@`. Не создавайте AAAA-запись, если на VPS не настроен публичный IPv6. Если DNS-провайдер умеет проксировать трафик, на время первой установки включите режим «только DNS».

Проверьте запись на своём компьютере:

```bash
nslookup dm.example.com
```

В ответе должен появиться публичный IPv4 вашего VPS. Распространение DNS иногда занимает от нескольких минут до нескольких часов. Не запускайте установку, пока домен показывает старый или чужой IP.

## 3. Установите приложение

Откройте веб-консоль VPS у провайдера или подключитесь по SSH. Войдите как `root`, затем по очереди выполните:

```bash
apt update && apt install -y git
git clone --depth 1 --branch v0.1.2 https://github.com/musa1756/inst_dm.git /tmp/inst_dm
cd /tmp/inst_dm
sudo bash scripts/install-vps.sh dm.example.com 203.0.113.10
```

Замените примеры своими доменом и публичным IPv4 VPS:

```bash
sudo bash scripts/install-vps.sh dm.example.com 203.0.113.10
```

Второй аргумент — публичный IPv4 именно этого VPS. Установщик остановится, если A-запись домена показывает другой адрес.

Установщик сам:

1. проверит Ubuntu, ресурсы сервера и DNS домена;
2. установит Docker и PostgreSQL;
3. сгенерирует уникальные пароли и ключи;
4. запустит приложение на вашем домене с HTTPS;
5. включит ежедневные резервные копии и автоматические security-обновления Ubuntu.

В конце появится строка `Admin password`. Сразу сохраните этот пароль в менеджере паролей: повторно он не показывается.

Не фотографируйте и не отправляйте кому-либо экран со строкой `Admin password`. Случайный пароль — это защита, а не проблема: он создаётся только для вашей установки и имеет существенно больше стойкости, чем короткий пароль, придуманный вручную.

После установки настройте вход на VPS по SSH-ключу. Отключать парольный SSH-вход можно только после того, как вы открыли **второе** соединение по ключу и убедились, что оно работает; иначе можно потерять доступ к серверу. Если вы не уверены, оставьте этот шаг AI-агенту или поддержке VPS, но не передавайте им приватный ключ.

## 4. Проверьте сервер и войдите в Inst DM

Выполните на VPS:

```bash
cd /opt/inst_dm
sudo docker compose ps
sudo docker compose exec -T app node -e 'fetch("http://127.0.0.1:3000/ready").then(async r => { console.log(await r.text()); process.exit(r.ok ? 0 : 1) })'
sudo systemctl status inst_dm-backup.timer --no-pager
```

Ожидаемый ответ: `{"ok":true,"database":true,"worker":true}`. В списке контейнеров `db`, `app` и `caddy` должны быть запущены.

Откройте выданный установщиком HTTPS-адрес. Получение первого сертификата иногда занимает 1–2 минуты.

Введите `Admin password`, откройте раздел **Подключение** и пока оставьте страницу открытой. На ней показаны значения, которые понадобятся Meta:

- OAuth callback;
- Webhook;
- маркер Webhook — на экране он скрыт, но копируется кнопкой;
- URL деавторизации;
- URL удаления данных;
- политика конфиденциальности.

## 5. Создайте приложение Meta

1. Откройте [Meta for Developers](https://developers.facebook.com/apps/) под своим аккаунтом Meta.
2. Нажмите **Create app / Создать приложение** и задайте название.
3. Выберите сценарий **Управление сообщениями и контентом в Instagram**. Бизнес-портфолио можно не подключать. Если Meta спросит тип приложения — выберите **Business**.
4. Откройте **Настройки приложения → Основное** и заполните:
   - **Домены приложений** — ваш домен;
   - **URL Политики конфиденциальности** и **URL-адрес Пользовательского соглашения** — значение `Политика` из Inst DM;
   - **Удаление данных пользователей** — выберите **URL обратного вызова для удаления данных** и вставьте значение `Удаление данных`;
   - **Категория** — например, **Бизнес и страницы**.

   Нажмите **Сохранить изменения**. ID и секрет приложения на этой странице в Inst DM **не** вставляются.
5. Откройте **Сценарии использования → Instagram → Настроить → Настройка API со входом через Instagram**.
6. Добавьте разрешения:
   - `instagram_business_basic`;
   - `instagram_business_manage_comments`;
   - `instagram_business_manage_messages`.

Для работы только с вашим аккаунтом или аккаунтом тестировщика отдельное SaaS-приложение и передача Instagram-пароля не нужны.

Для каждой установки создавайте новое приложение: у приложения один адрес Webhook, поэтому приложение от другой установки не подойдёт.

## 6. Добавьте Instagram-аккаунт тестировщиком

1. В Meta for Developers откройте **App roles / Роли в приложении**.
2. Добавьте нужный Instagram-аккаунт как **Instagram Tester**.
3. На телефоне войдите именно в этот Instagram-аккаунт.
4. В Instagram откройте **Настройки и конфиденциальность → Разрешения сайтов / Apps and websites → Приглашения тестировщика** и примите приглашение.

Название пункта в приложении Instagram может немного отличаться. Пока приглашение имеет статус «На рассмотрении», аккаунт не появится в API Setup.

В блоке **«2. Сгенерируйте маркеры доступа»** ничего не нажимайте: кнопка «Сгенерировать маркер» и переключатель подписки там не нужны. Inst DM сам получит токен и включит подписку при подключении.

## 7. Заполните адреса Meta

В блоке **«Настройте вход в бизнес-аккаунт Instagram»** нажмите **Настроить** и вставьте значения из раздела **Подключение** Inst DM:

- **Valid OAuth redirect URI** → `OAuth callback`;
- **Deauthorize callback URL** → `Деавторизация`;
- **Data deletion request URL** → `Удаление данных`.

В основных настройках приложения укажите:

- **Privacy Policy URL** → значение `Политика`;
- категорию приложения и контактный email, если Meta их требует.

Сохраните настройки.

## 8. Настройте Webhooks

В блоке Instagram Webhooks:

1. В **Callback URL** вставьте значение `Webhook` из Inst DM.
2. В **Verify token / Подтверждение маркера** вставьте скопированный `Маркер Webhook`.
3. Нажмите **Verify and save / Подтвердить и сохранить**.
4. Включите подписки как минимум на:
   - `comments`;
   - `messages`;
   - `messaging_postbacks`.

Все остальные поля (`live_comments`, `message_edit`, `message_reactions`, `messaging_referral`, `messaging_seen` и другие) выключите, если Meta включила их: Inst DM их не обрабатывает и покажет как нераспознанные события.

Meta доставляет webhooks только приложению со статусом **Live / Опубликовано**. После подключения аккаунта (шаг 9) откройте в меню слева **Публикация** и опубликуйте приложение, заполнив то, что попросит Meta. Если панель требует App Review, выполняйте требования, показанные именно в вашей панели Meta.

## 9. Подключите аккаунт

1. Вверху страницы **Настройка API со входом через Instagram** скопируйте **ID приложения Instagram** и **Секрет приложения Instagram** (кнопка «Показать»). Это не те ID и секрет, что в «Основных настройках».
2. В Inst DM откройте **Подключение**.
3. Вставьте App ID и App Secret. Поле App Secret сначала полностью очистите: браузер часто сам подставляет туда сохранённый пароль администратора, и поле становится жёлтым.
4. Оставьте рекомендованную версию Graph API и нажмите **Сохранить и подключить**.
5. На официальной странице Instagram разрешите доступ нужному Professional Account.

Пароль Instagram вводится только на странице Meta/Instagram. Никогда не вставляйте его в Inst DM, `.env`, терминал или сообщение другому человеку.

После возврата в панель должны стать зелёными:

- токен Instagram;
- подписка Webhooks;
- обработчик очереди.

Строка «Последний Webhook» станет зелёной после первого реального комментария или сообщения. Если приложение ещё не опубликовано, опубликуйте его сейчас (см. шаг 8).

## 10. Создайте первое правило и проверьте

1. Нажмите **Создать правило**.
2. Выберите триггер **Комментарий**.
3. Для первого теста выберите конкретный Reel/Post и ключевое слово, например `гайд`.
4. Включите ответ на комментарий и/или сообщение в Direct. Для кнопки укажите текст до 20 символов и HTTPS-ссылку, например на Telegram-канал `https://t.me/<канал>`: нажатия на кнопку считаются в аналитике.
5. Сохраните активное правило.
6. Оставьте новый комментарий со второго Instagram-аккаунта, который не является автором публикации.

Проверьте публичный ответ, Direct и запись в **Журнале**. Не используйте старый уже обработанный комментарий: защита от дублей намеренно не запускает то же правило второй раз для того же человека и публикации.

## Резервные копии

Backup сохраняет правила, очередь, аналитику, подключение Meta и ключ расшифровки. Он нужен, если обновление окажется неудачным, база повредится или что-то будет случайно удалено.

Копия создаётся ежедневно и хранится 14 дней:

```bash
sudo ls -lh /var/backups/inst_dm
```

Создать копию вручную:

```bash
sudo /opt/inst_dm/scripts/backup.sh manual
```

Проверить последнюю копию без изменения рабочей базы:

```bash
sudo /opt/inst_dm/scripts/verify-backup.sh
```

Архив содержит секреты. Не публикуйте его, не прикладывайте к GitHub Issues и периодически скачивайте свежую копию в своё защищённое хранилище.

Ежедневная задача проверяет, что дамп PostgreSQL и архив читаются. Команда `verify-backup.sh` делает более полную проверку: восстанавливает дамп в отдельную одноразовую БД, проверяет обязательные таблицы и удаляет её, не затрагивая рабочую базу.

### Восстановление из backup

Восстановление заменяет содержимое рабочей базы. Сначала проверьте архив и убедитесь, что выбрали точный файл:

```bash
sudo /opt/inst_dm/scripts/verify-backup.sh /var/backups/inst_dm/<archive>.tar.gz
sudo INSTDM_RESTORE_CONFIRM=RESTORE_INST_DM \
  /opt/inst_dm/scripts/restore-backup.sh \
  /var/backups/inst_dm/<archive>.tar.gz
```

Перед заменой базы скрипт создаёт ещё одну страховочную копию. По умолчанию он оставляет текущий `.env`. При восстановлении на новом VPS можно также вернуть production-конфигурацию из архива, осознанно добавив `INSTDM_RESTORE_ENV=1`; архив содержит рабочие секреты, поэтому используйте этот флаг только для своего доверенного сервера.

После восстановления проверьте `/ready`, подключение Instagram и правила до возобновления реального трафика.

### Быстрая диагностика

Безопасный read-only отчёт о сервере:

```bash
sudo /opt/inst_dm/scripts/doctor.sh
```

## Обновления

Установки пользователей не обновляются автоматически от push разработчика. После объявления новой проверенной версии запустите команду с её тегом, например:

```bash
sudo /opt/inst_dm/scripts/update-vps.sh v0.1.2
```

Перед обновлением автоматически создаётся backup. Новая версия собирается отдельно и заменяет работающую только после успешной проверки `/ready`; при ошибке возвращается предыдущий Docker-образ.

Не запускайте обновление на `main`, если не готовы тестировать промежуточную версию.

## Частые проблемы

### Сайт не открывается

Проверьте, что TCP-порты 80 и 443 открыты в панели VPS, а IP указан верно. Затем выполните:

```bash
cd /opt/inst_dm
sudo docker compose ps
sudo docker compose logs --tail=100 caddy app
```

### Meta не принимает Webhook

- скопируйте URL и маркер заново, без пробелов;
- убедитесь, что сайт открывается по HTTPS;
- проверьте, что приложение Meta опубликовано, если панель прямо этого требует;
- не используйте OAuth callback вместо Webhook URL.

### Комментарий не запускает правило

- комментарий должен быть новым и оставленным другим аккаунтом;
- правило должно быть активно и подходить публикации/ключевому слову;
- поле `comments` должно иметь активную webhook-подписку;
- откройте **Журнал** и **Подключение → Проверить**.

### Безопасная диагностика

При обращении за помощью можно прислать вывод:

```bash
cd /opt/inst_dm
sudo docker compose ps
sudo docker compose logs --tail=150 app
```

Перед отправкой удалите из текста токены, App Secret, пароли, содержимое `.env`, IP при желании и персональные данные.
